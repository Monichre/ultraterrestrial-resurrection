**Scope:** Read-only. No ingestion run, no network fetch, no writes to `data/`.
**Updated:** 2026-08-07 — closed the `main.py --no-kb` UNVERIFIED item (§3.3, §5, §6): confirmed by direct read of `main.py` and `lib/youtube.py` that `--no-kb` does not provide a lightweight peek. See changelog note at the bottom of §3.

## Executive summary

**Recommendation: (c) keep them separate, with a stated boundary.** The global `youtube-content` skill (`/Users/liamellis/skills/media/youtube-content/`) is a thin, stateless wrapper around `youtube-transcript-api` for single-video, throwaway conversational transforms (chapters/summary/thread/blog) — it has no retry logic, no quality gate, no persistence, and no concept of "safe to embed." The repo's `dy` pipeline (`apps/disclosure-rag/scripts/playlist_ingestion.py` + `lib/transcript_fidelity.py` + `processing/rag_prompt_pipeline.py`) is the only one of the two with fidelity scoring, quarantine, an Evidence/Inference separation (ADR-0001), checkpointed state, and provenance reporting — everything this project's epistemic-honesty constraint requires before content reaches the RAG corpus. They are not redundant: the skill's output-format transforms (chapters/threads/blogs) are a genuinely distinct capability `dy` doesn't have in code, and — now confirmed by reading `main.py` and `lib/youtube.py` directly — **`dy` also has no lightweight, side-effect-free "just show me the transcript" path at all**: `main.py --no-kb` still runs the full LLM-calling RAG pipeline and writes four files to disk per video (see §3.3). The skill's niche is therefore broader than content transforms alone; it's currently the *only* zero-cost, zero-write transcript lookup in this toolset. Two items are worth porting into `dy`: a `/live/` URL-parsing branch (trivial), and — more valuably now — a genuine lightweight peek command built directly on `lib/youtube_transcript_enhanced.py`, bypassing `generate_transcript()`'s LLM/file-write path entirely. Everything else should stay on its own side of the line. No hard dependency conflict exists between the two (both use `youtube-transcript-api` 1.x, different patch versions, fully isolated environments).

## 2. Overlap and redundancy

The only genuine overlap is the raw fetch step, and even there it's a subset relationship, not duplication:

- Skill: `scripts/fetch_transcript.py:63-67` — `YouTubeTranscriptApi().fetch(video_id, languages=languages)`, one call, first match, done.
- `dy`: `lib/youtube_transcript_enhanced.py:356-391` `_fetch_once()` — `.list(video_id)` then walks `_candidates()`'s four-tier preference order, catching and classifying exceptions per candidate rather than per call.

Both depend on the same library, `youtube-transcript-api`, both on the 1.x line:
- `apps/disclosure-rag/requirements.txt:39` pins `youtube-transcript-api>=1.2  # 1.x exception classes + proxies module are required` — this constraint was added in the currently-uncommitted diff (`git diff apps/disclosure-rag/requirements.txt` shows the old line was an unpinned `youtube-transcript-api`). Installed in the repo `.venv`: **1.2.2**.
- The global skill's environment (managed via `uv`, no `pyproject.toml` found anywhere under `/Users/liamellis/skills/`) has **1.2.4** installed (`uv pip list`).

No conflict: same major version, both post-1.0 (needed for the exception classes and `proxies` module `dy` imports at `lib/youtube_transcript_enhanced.py:34-48`), fully separate environments (see §6).

`rag_prompt_pipeline.py`'s chunking stage does **not** overlap with the skill's chapters/summary/thread/blog transforms, despite both being "take transcript, produce structured text." The pipeline's own docstring draws the line: *"Chunk bodies remain Evidence-only (ADR-0001): never embed agent Inference"* (`processing/rag_prompt_pipeline.py:9-10`). Its chunks are RAG-indexing units, not reader content. The skill's transforms are explicitly interpretive/summarizing. These are different jobs that happen to both start from a transcript.

## 3. What the skill has that `dy` lacks — worth adopting

1. **`/live/` URL parsing.** `scripts/fetch_transcript.py:30` includes a `live/` branch in its video-ID regex. `dy`'s `extract_video_id` (`lib/youtube_transcript_enhanced.py:165-206`) has an explicit if/elif chain for `youtu.be`, `/shorts/`, `/watch`, `/embed/` and `/v/` but **no `/live/` case** — a livestream URL passed to `dy` would fall through to `return None`. Concrete port: add `elif p.path.startswith("/live/"): return p.path.split("/")[2] if ... else None` mirroring the shorts branch at lines 189-191. Trivial, a few lines.

2. **Content-transformation formats** (chapters, summary, chapter-summaries, Twitter thread, blog post, quotes — `SKILL.md:42-61`, `references/output-formats.md`). Confirmed this does *not* overlap with `rag_ingestion`'s chunking (see §2) — it's a genuinely distinct, currently-absent capability in `dy`. Porting cost is low in principle (it's prompt-engineering/agent-workflow, not a script dependency), but see §4/§6: this output is generative paraphrase and must not be treated as embeddable Evidence if ported.

3. **Lightweight one-shot text output** (`--text-only`, `--timestamps` on `fetch_transcript.py`) for a quick "just show me the transcript" lookup outside the full ingestion pipeline. **This item is now closed — `dy` has no equivalent, confirmed by direct read of `main.py` and `lib/youtube.py`:**

   - `main.py:1062` sets `add_to_kb = not args.no_kb` and passes it into `process_url()`/`process_file()`. For a YouTube URL, `process_url()` (`main.py:312-431`) calls `process_youtube_url_enhanced(url, upload, add_to_kb)`, which (per `lib/knowledge_base_service.py`, not fully re-traced here) calls `lib/youtube.py`'s `generate_transcript(url)` — note the signature: **`generate_transcript` takes only `url`, no `add_to_kb` parameter at all** (`lib/youtube.py:200`). So nothing downstream of the transcript fetch inside that function can be gated by `--no-kb`.
   - Unconditionally, on every call, `generate_transcript()`: runs `analyzer.analyze_content()` (`lib/youtube.py:217`, an LLM summarization call), runs the full 5-stage `analyzer.process_for_rag()` pipeline (`lib/youtube.py:227`, classification → content_analysis → chunking → NER → validation — multiple further LLM calls via `processing/rag_prompt_pipeline.py`), then writes **four files to disk**: the raw transcript (`write_transcript_to_file`, `lib/youtube.py:266-268`), an analysis/summary file (`lines 270-272`), a `<name>_rag_pipeline.json` (`lines 274-280`), and a `<name>_metadata.json` (`lines 303-307`) — plus a best-effort Mem0 write (`lines 283-301`).
   - `--no-kb` only skips what happens *after* this: KB storage/`doc_id` creation, the second doc_id-scoped entity-extraction pass, CocoIndex KG construction, and (for files) processing-queue relocation — confirmed directly for the file path by `main.py:590-820`, where the entire `if add_to_kb:` block starts *after* the RAG pipeline block at `lines 494-538` and the (also unconditional) `<stem>_rag_pipeline.json` write. The `_build_dry_run_plan()` function (`main.py:883-957`) independently corroborates this: for a URL, `"Would run: {extraction stage}"` (`line 895-896`) is emitted *before* the `if add_to_kb:` branch (`line 897`) that gates only "knowledge base entry... entity extraction... knowledge graph."
   - **Conclusion: there is no command in `dy`/`main.py` that fetches a YouTube transcript to stdout without both incurring real LLM API cost and writing files to disk.** `--no-kb` is not a peek flag — it only trims the tail of the pipeline (KB write onward), not the LLM-calling head. The skill's `fetch_transcript.py --text-only` remains the only zero-cost, zero-write option for a single-video lookup anywhere in this toolset.

## 4. What `dy` has that the skill lacks

This is where the epistemic-honesty gap is concrete, not abstract:

- **Fidelity scoring.** `lib/transcript_fidelity.py:165-254` `review_transcript()` — weighted composite (coverage .30, density .20, gaps .15, artifacts .15, repetition .20), verdicts `pass`(≥0.7)/`review`(0.45-0.7)/`fail`(<0.45). The skill has **zero** quality signal: it would hand a 40%-coverage, artifact-heavy auto-caption transcript straight into a "blog post" transform with no warning beyond a subjective "re-read for coherence" step (`SKILL.md:69`).
- **Quarantine gate.** Fidelity `fail` or below `--min-fidelity` → `status="quarantined"`, transcript and report kept on disk but **not ingested** (`scripts/playlist_ingestion.py:274-278`; `references/playlist-ingestion.md:41-43`).
- **Evidence/Inference separation (ADR-0001).** `processing/rag_prompt_pipeline.py:9-10` docstring is explicit; enforced at `lines 288-301` where chunks a validation pass marks `safe_for_rag_index: False` are excluded from `embeddable_texts`. This is exactly the "invent/paraphrase/lossily summarize into the corpus" guard the task brief calls a hard constraint — and it's precisely what the skill's chapters/summary/thread/blog output would violate if fed into the KB directly, since those formats are inherently paraphrase with no sourcing discipline documented anywhere in `SKILL.md`.
- **Full provenance chain.** `doc_id`, `fidelity`, `rag_status`, timestamps recorded per video in `state.json` (`scripts/playlist_ingestion.py:184-194`); per-run markdown report (`scripts/playlist_ingestion.py:325-346`). The skill produces stdout only — nothing survives the conversation.

## 5. Recommendation

**(c) Keep them separate, with a stated boundary:**

- The global `youtube-content` skill is for **disposable, single-video, out-of-corpus** conversational work — "summarize this video for me right now," not "add this to the knowledge base."
- `dy` (via `scripts/playlist_ingestion.py` / `main.py`) remains the **only** path allowed to write into the corpus, because it's the only one with fidelity gating, quarantine, and the Evidence/Inference split.
- Porting worth doing, low cost: the `/live/` URL branch (§3.1, a few lines). Also worth doing, now that §3.3 confirms the gap is real rather than hypothetical: a genuine lightweight peek command in `dy` — a thin CLI wrapper directly on `lib/youtube_transcript_enhanced.get_metadata_and_transcript_api_first()` that stops after formatting the transcript, never calling `generate_transcript()`'s LLM/file-write path. This both closes the capability gap and gives operators a free way to sanity-check a video before spending an ingestion run's LLM budget on it.
- Not worth porting: the output-format transforms as a `dy` feature, because doing so would put generative-paraphrase code inside the pipeline that's supposed to enforce Evidence-only chunking. If a user wants both a corpus entry *and* a reader-facing summary of the same video, that should be two separate operations, not one pipeline doing both.
- Retire nothing — the skill is not subsumed; it does a job `dy` deliberately doesn't do.
