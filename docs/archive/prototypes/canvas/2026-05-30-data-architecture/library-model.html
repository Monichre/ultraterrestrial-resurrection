The Library + the vectorization fork

Corrected model: the Library is the canonical, immutable evidence store. It has two jobs — host the files, and feed the vectorizer. The question is where vectorization happens.

📚 The Library

Object storage for canonical evidence. PDFs, image sets, transcripts, video. Versioned, content-addressed, read-only to users.

immutable · data sanctity
Role 1 — Host: serve original files to the frontend (viewer, download, citation source).
Role 2 — Feed: emit each file to the ingestion/vectorization layer → searchable corpus.

Pick one — where should vectorization live?

A

Owned ingestion pipeline → your own vector store

A worker reads from the Library, chunks, embeds (you pick the model), writes vectors into pgvector next to your relational data. Full control of chunking & re-embedding; vectors are SQL-queryable and live with CRUD records.

Library → [chunk+embed worker] → pgvector(documents, chunks) ← same DB as entities
B

Platform-native / storage-integrated embeddings

The storage platform vectorizes on upload via triggers/queues (e.g. Supabase automatic embeddings). You still own the model & vectors, but the platform orchestrates the "file lands → embed → index" flow. Less glue code to maintain.

Library upload → trigger → embed job → pgvector (managed by platform)
C

Managed black-box (today's OpenAI Vector Store)

Upload file → provider auto-chunks, embeds, and serves retrieval via API. Near-zero effort, but you don't control chunking, can't SQL-query vectors, and the corpus stays a separate silo from your CRUD data. This is the current state's weakness.

Library → OpenAI Vector Store (opaque) → file_search API only

My lean: A or B — both keep vectors next to your relational data so the agent's brain and the frontend share one source of truth. The choice between them is mostly "how much do you want the platform to do for you," which folds neatly into the platform decision. Click whichever pulls you, or tell me what you're weighing.
