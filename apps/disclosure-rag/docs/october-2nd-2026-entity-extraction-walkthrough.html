What broke entity extraction, and how to fix it

Walkthrough written October 2nd, 2026, for a reader who wasn't in the code. Nothing described as a fix below has been done yet. Every number was checked against the files on disk or git history.

Sections: The short version · Your design · What happened, in order · The evidence · Why 8-minute pieces were wrong · What's what: the files · The roundtable · The proposed fix · What you need to decide · Terms

1. The short version

In four sentences

Your ingestion design was: one model reads the whole transcript and writes a summary containing every entity, then a second step pulls those entities out of the summary and puts them in the database. On August 14th, 2026, a commit titled "here goes" quietly switched the second step to take entities from a different stage that only reads the first 24,000 characters (about 25 minutes of a podcast). Separately, the database step still points at Xata, which was retired, so nothing has been written to the database from this path since. Then on October 1st–2nd, 2026, I (Claude) made it worse by building a parallel pipeline that cut the Grusch podcast into 8-minute pieces instead of fixing the real break.

2. Your design, and why it worked

You wrote this down on July 9th, 2025, in apps/disclosure-rag/lib/entity_extraction/docs/ENTITY_EXTRACTION_PRESERVATION_PLAN.md. That document marks the extraction workflow "PRESERVE UNCHANGED".

Transcript
the whole episode
→
Layer 1: the summary
one model call reads everything; writes a narrative summary plus every entity it found
→
Layer 2: extraction
EntityExtractionAgent turns the summary's entities into structured records
→
Database
search for each entity; create it if it's missing

Why reading the whole thing at once matters

  • Context. When the guest says "he" two hours in, the model already knows who was introduced at minute twelve. Later corrections override earlier remarks.
  • Natural deduplication. A person mentioned fifty times becomes one entity, not fifty fragments that need merging.
  • A readable checkpoint. The summary is something you can open and judge before anything touches the database.
  • Cost. One call per source. A 2.5-hour transcript is about 40,000 tokens, which current models read in one request.
  • Clean input for layer 2. Extraction reads a dense, organized summary instead of a noisy transcript full of crosstalk.

Example of it working: the Bob Lazar / Don Garlits interview (packages/knowledge-base/sources/transcripts/motorhead-garage/PmclCzGFotM/). Its summary has Personnel, Key Events, Organizations and Technical Evidence sections, and the entity file built from it is clean: one person, two events, two organizations, two locations, three technologies.

5. Why cutting a podcast into 8-minute pieces was wrong

This is what my October pilot did, and it's the same instinct behind the capped stage.

  • Each piece is blind. A model reading minutes 96–104 doesn't know who "this guy" is, so it records "this guy".
  • The same question gets answered 19 times. Every passage separately decided whether David Grusch deserved a record. That's the repetitive vote trail you found in reconciled.json.
  • Breaking it up creates repair work. The fragments needed a reconciliation step (619 decisions down to 521) plus 34 merges for a human to review. Reading the whole source never has that problem.
  • It costs more for a worse result. Dozens of calls instead of one.
  • It put files in the wrong place. Output went to packages/knowledge-base/derived/reports/…/corrected/ with generic names, instead of the source's own folder with dy naming.

Where they agree

  1. Reinstate the summary as the entity source. Undo the August 14th switch so layer 2 reads entities from the summary again.
  2. Not a wholesale rollback. Keep what's been added since: telling "failed" from "found nothing", reading old result files, frontier model routing, and the hold-on-blocked fix.
  3. Replace Xata with the Postgres code that already exists in lib/entity_resolution/store.py, through a small adapter. Don't port the old Xata creator.
  4. The capped stage stops making entity decisions. It stays for search chunks; the trace map becomes a navigation aid.
  5. The biggest hidden risk is the 4,000-token output limit on both layers. A long episode can have more entities than fit. The cut-off reply fails to parse and silently becomes "no entities", the same failure in a new place.

Only Astra caught

  • The extraction schema asks the model for only 7 entity types plus relationships. Technologies, dates, testimonies and documents aren't in it. Half right. Checked against the live database (29 tables), not a migration file. The extractor covers 7 record tables (topics, key_figures, events, organizations, locations, artifacts, sightings) but misses two more: testimonies (178 rows) and documents (189 rows). Technologies and dates have no table, so they stay out. Relationships belong in the junction tables (organization_members, topics_testimonies, event_subject_matter_experts and others) and in entity_aliases.
  • Sightings come back with blank names: the schema asks for description, the converter reads name.
  • The quick wrapper keeps only names, dropping confidence, context, metadata and relationships.
  • The Postgres matcher accepts a run ID but ignores it, so one source's run could resolve another source's pending entities.
  • Extraction logic also does validation inside the capped stage's loop; that has to be separated before switching it off.
  • The summary prompt still asks for credibility scores.

Only Sonnet caught

  • The processor stops to ask yes/no questions. Batch reruns need that switched off.
  • Pass full structured entities to the Postgres matcher, not name lists, or confidence and context are lost.
  • Someone edited the "PRESERVE UNCHANGED" plan (the Upstash removal above).
  • Judge the fix on more than one run; output varies between identical runs.

10. Terms

  • dy: the command that ingests a YouTube video or web page into the knowledge base.
  • Entity: a person, organization, event, location, technology, artifact or sighting named in a source.
  • NER (named-entity recognition): a model pass that lists entities in a piece of text.
  • Chunk: a slice of a source stored for search. Chunks are for finding passages, not for deciding what entities exist.
  • Trace map: a file linking chunks to timestamps in the video.
  • Xata: the old hosted database. Retired; replaced by Postgres on Neon.
  • Output-token limit: the most text a model may write in one reply. Too low, and a long list gets cut off mid-way.
  • Roundtable: independent read-only reviews from different models, compared side by side.
