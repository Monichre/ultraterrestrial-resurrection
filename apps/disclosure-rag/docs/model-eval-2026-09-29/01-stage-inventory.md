# 01 — Ingest pipeline: every model call, per stage

Written 2026-09-29 03:48 CDT. Read-only inventory of the `dy` / process-file / playlist ingest paths. Method: the `graft` CLI was not on PATH (`graft/` is a doc tree only), so everything below comes from grep + source reads. Call chain reference: [apps/disclosure-rag/docs/CALL_CHAIN.md](apps/disclosure-rag/docs/CALL_CHAIN.md).

## Headline facts (these change model choice)

1. **There is no per-stage model routing today.** Every task in [packages/ai/prompts/llm_routing.yaml](packages/ai/prompts/llm_routing.yaml) points at the same `*preferred` + `*fallback` anchors, and [apps/disclosure-rag/lib/llm_router.py:360](apps/disclosure-rag/lib/llm_router.py#L360) appends `defaults.chain` too. The same flagship (`openai/gpt-6-astra`) serves classification, chunking, NER and QA alike.
2. **Chunking is an LLM prompt on `dy`** (`rag_ingestion`, strict schema, 16k output tokens, re-emits source verbatim). The Postgres `document_chunks` vectors came from a different, code-based word-count chunker in [packages/db/scripts/rebuild/ingest.py:74](packages/db/scripts/rebuild/ingest.py#L74). The LLM's `embeddable_texts` are not vectorized anywhere on `dy`.
3. **Only one stage is long-context:** `narrative_summary` gets the full, untruncated transcript ([apps/disclosure-rag/lib/youtube.py:423](apps/disclosure-rag/lib/youtube.py#L423)). Every RAG stage is capped at `MAX_SOURCE_CHARS` = 24,000 chars ([apps/disclosure-rag/processing/rag_prompt_pipeline.py:66](apps/disclosure-rag/processing/rag_prompt_pipeline.py#L66)).
4. **NER + validation cover only the first 8 chunks** (`RAG_PIPELINE_MAX_NER_CHUNKS`, [apps/disclosure-rag/processing/rag_prompt_pipeline.py:65](apps/disclosure-rag/processing/rag_prompt_pipeline.py#L65)). Chunks 9+ are never NER'd or validated but still land in `embeddable_texts`.
5. **Only `rag_ingestion` sends a schema over the wire.** `content_analysis` and `ner` have registry schemas that are never sent ([apps/disclosure-rag/processing/rag_prompt_pipeline.py:97](apps/disclosure-rag/processing/rag_prompt_pipeline.py#L97)).
6. **No embedding call, OCR model, or transcription model runs on the `dy` CLI path.** Embeddings happen server-side at sinks (OpenAI vector store, Upstash Search) or in the separate rebuild script.

### Calls per document

| Path | LLM calls (happy path, before repair retries) |
| --- | --- |
| YouTube (`dy <url>`, playlist) | 1 narrative + 1 classify + 1 content_analysis + 1 rag_ingestion + ≤8 NER + ≤8 validation = **≤20** (+1 coherence with `--llm-review`) |
| Local file (`dy <path>`) | same minus narrative = **≤19** |
| Web (`dy <web-url>`) | 2× narrative (processor + kb_service) + 4–19 RAG calls + ≤10 image "analysis" + ≤5 linked-PDF narrative = **up to ~36** |

Each JSON stage can add one parse-repair retry on the same task ([apps/disclosure-rag/processing/rag_prompt_pipeline.py:270](apps/disclosure-rag/processing/rag_prompt_pipeline.py#L270)).

## Contradictions (most consequential first)

1. **Per-stage routing is declared but not real.** Nine tasks exist in llm_routing.yaml; all reference the same two anchors, and `chain_ids` appends `defaults.chain`. Changing one stage's model means editing that task's list off the shared anchor.
2. **YAML task budgets are dead config.** `complete()` defaults are constants (not `None`), and `get_task_params` is never called, so the yaml's "apply only when the caller passes None" rule never fires. Examples of drift: NER is 4000 in the registry vs 1200 in the yaml; `narrative_summary` is 0.2 temp in the registry ([packages/ai/prompts/sets/disclosure/research.v1.yaml](packages/ai/prompts/sets/disclosure/research.v1.yaml)) vs 0.1 at the call site (call site wins).
3. **Model ids live in two places.** The yaml header says "llm_fallback.py holds no model ids", but `FRONTIER_FALLBACK_CHAIN` does, with a different order (DeepSeek first, not GPT-6 Astra). It serves `entity_extraction_agent` (yaml task `entity_extraction` added 2026-09-29, but the call site passes no `task_id`) and coherence review whenever a provider hint is set.
4. **Provider preference is ignored on routed calls.** `complete()` calls `router.get_ordered_tiers_for_task(task_id)` without `prefer_provider` ([apps/disclosure-rag/lib/llm_fallback.py:965](apps/disclosure-rag/lib/llm_fallback.py#L965)), so `RAG_PIPELINE_PROVIDER` does nothing for pipeline stages. Also `get_fallback()` is a singleton ([apps/disclosure-rag/lib/llm_fallback.py:1098](apps/disclosure-rag/lib/llm_fallback.py#L1098)): the first caller's `prefer_provider` wins process-wide.
5. **Unused / wrong yaml statements.** `requires` does not filter tiers; `pdf_processing` is never read; the "parse_repair uses defaults.chain" comment has no matching code — repair reuses the stage's own `task_id`.
6. **CALL_CHAIN.md is wrong about the web path.** WEB-CHAIN-01 says web gets no `process_for_rag`; [apps/disclosure-rag/processing/web_content_processor.py:724](apps/disclosure-rag/processing/web_content_processor.py#L724) runs it. No `*_rag_pipeline.json` write was found in the kb_service web branch, so downstream entity processing likely finds no NER for web docs (unverified).
7. **Two chunkers.** `dy` chunks with an LLM (`rag_ingestion`); the live Postgres chunk vectors came from word-count code chunking in the rebuild script. Neither consumes the other's output.
8. **Web image analysis never sends the image.** `analyze_image_content` passes only a text prompt to `narrative_summary`, up to 10 calls per page for no input signal. Vision-capable tiers exist in the yaml (`capabilities.vision`) but nothing uses them.

## Implications for model assignment (input to the eval)

- **Long-context prose:** stage 3 only. Must handle 15k–30k+ tokens of transcript.
- **Output-heavy strict JSON:** stage 6. Needs strict-schema support and a ≥16k output budget. Cost scales with the source size, not with a summary.
- **Cheap/fast extraction candidates:** stages 4, 7, 8 (small inputs, ×8 fan-out for 7 and 8), and stage 2.
- **Unassigned model slots:** OCR for scanned local PDFs (none today), vision for web images (none today), and the entity-resolution review band.
